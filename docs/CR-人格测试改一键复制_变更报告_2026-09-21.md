## 〇、本轮的由来：第五轮方案被证伪

### 第五轮做了什么

用 `wx.setClipboardData` 的替代品 —— **二维码长按识别**（用户长按二维码 → 微信识别 → 打开网页），理由是"不触碰隐私接口、不受业务域名限制"。

### 真机结果（用户截图证据）

长按二维码后的菜单**只有**：

```
转发给朋友 / 保存图片 / 收藏 / 翻译图片中的文字 / 取消
```

**没有「识别图中二维码」。** 方案不可用。

### 权威口径（已检索确认）

> **目前支持的长按识别的二维码都是微信体系下的**（小程序码 / 微信个人码 / 企业微信个人码 / 普通群码 / 互通群码 / 公众号二维码）。
> **对于第三方生成的二维码不支持长按识别**；第三方二维码长按后可转发，转发后的图片在聊天场景才可识别。
>
> —— 微信服务市场官方 QA《支持识别的码类型与场景如何?》

### 根因定性

我们生成的是**普通 URL 二维码**（指向 `16personalities.com` 等网站）→ **不在微信长按识别支持范围内**。

**这是码类型的硬限制**：
- ❌ 不是 `show-menu-by-longpress` 未生效（该属性作用是"出现长按菜单"，不是"支持识别任意码"）
- ❌ 不是 `previewImage` 与页面内 `<image>` 的差别（两者对第三方码同样不支持）

### 🔴 我的判断错误（已记录进长期记忆）

核实 `show-menu-by-longpress` 时，只确认到「该属性开启即出现长按菜单」这一层，**没有继续追问「该能力对哪些类型的码成立」**。

后果：把「属性已开启」误当成「功能可用」，并**把不可能通过的检查写进了验收清单**（第五轮报告第六节第 3 条"真机长按应出现识别入口"）。

**教训：核实属性/开关是否生效时，必须追到「该能力对什么类型的输入成立」这一层。**
