## 0. 问题定性

### 现象

用户输入「现在几点」，系统进入哲学回答链路，并在回答中自曝「无法联网、无法获取时间」。

### 根因

这**不是**知识缺失，**不是**模型能力问题，而是**架构分层缺失**。

修复前，chat 云函数只有两条轨道：

| 轨道 | 处理对象 |
|---|---|
| Knowledge Layer（RAG） | 经典知识、人生问题 |
| Freshness Layer | 现实事件背景（Phase Q 新增） |

「现在几点」既不是经典问题，也不是热点事件——它是**实时事实诉求**。没有对应轨道，它被默认路由进了 RAG，于是：

1. 检索层在 corpus.json 里找「时间」，召回一堆关于时间的哲学片段；
2. 生成层被迫用五段式回答一个只需要一行答案的问题；
3. 模型为解释自己答不上来，自曝「无法联网」——把**架构缺陷**说成了**能力缺陷**。

### 三个必须区分的判断

| 错误归因 | 正确归因 |
|---|---|
| 「模型不知道时间」 | 系统时钟一直可用，是没人去读 |
| 「需要给知识库补充时间知识」 | 时间是**运行时事实**，写进知识库即刻过期，是污染 |
| 「让 Prompt 学会回答时间」 | Prompt 无法产生事实，只会诱导编造 |

**结论：需要的是第三条轨道，而不是修补前两条。**

```

用户输入 ──────────▶│      intent router          │  （冻结 intent.js，只读消费）
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │   Capability Router  ★新增   │
                    │   实时事实诉求？              │
                    └───┬───────────────────┬─────┘
                   命中 │                   │ 未命中（返回 null）
                        ▼                   ▼
              ┌─────────────────┐   ┌───────────────────┐
              │  Tool 执行       │   │ Freshness Layer   │
              │  time/weather/   │   │ （Phase Q）        │
              │  calc/location   │   └─────────┬─────────┘
              └────────┬─────────┘             │ 未命中
                       ▼                       ▼
              ┌─────────────────┐   ┌───────────────────┐

              └────────┬─────────┘   └─────────┬─────────┘
                       └──────────┬────────────┘
                                  ▼
                            answerId + 安全检测 + 观测落库
```

### 三层边界（互不侵染，本次以静态扫描锁定）

| 层 | 数据来源 | 时效 | 输出形态 | 是否进 RAG |
|---|---|---|---|---|
| **Capability** | 运行时 / 系统服务 | 秒级 | 一行事实 + 可选邀请 | **绕过** |
| **Freshness** | 外部事实检索 | TTL 6h | 五段式思辨 | 供给背景 |
| **Knowledge** | corpus.json | 永久 | 五段式思辨 | 是 |

**硬性隔离约定（测试项 K 强制执行）**

- `capabilities/` 零引用 `corpus.json` / `rag.js` / `knowledgeRouter.js`
- `capabilities/` 零 embedding、零向量、零检索
- 唯一允许的冻结依赖：`intent.js` 的 `classifyIntent`，**只读**，仅用于危机让位
- **不向知识库新增任何「时间知识」**——实时事实进知识库即为污染

## 3. 调用链详解

```
maybeHandle(message, { history, location, now })
  │
  ├─① intent router
  │     classifyIntent(query, history)      ← 只读冻结 intent.js
  │     危机信号 → return null（交既有危机链路，能力层永不争抢）
  │
  ├─② Capability Router  router.route()
  │     ├─ 硬否决（veto）：工具词被哲学化使用 → return null
  │     │    veto-meaning / veto-opinion / veto-metaphor / veto-lifeadvice
  │     ├─ 软信号：情绪并存 → emotional=true（不否决，只改语气）
  │     └─ 命中判定：time / weather / calculation / location
  │
  ├─③ Tool 执行
  │     time      → 系统时钟，恒成功
  │     weather   → provider 查询，默认无源 → ok=false + 边界声明
  │     calculator→ tokenizer → RPN → 求值
  │     location  → 前端授权位置，无则边界声明
  │
  ├─④ Response Formatter  formatter.buildAnswer()
  │     ok=true  → 事实 + \n\n + 一句邀请
  │     ok=false → 仅边界声明（不追加邀请，避免语气错位）
  │
  └─⑤ 返回 { mode:'capability', answer, citations:[], capability:{…} }
        → chat/index.js 继续走 answerId / 出参安全检测 / 观测落库
```

### 关键设计判断

#### ① 为什么置于 Freshness 之前？

实时事实诉求的确定性最高，且与思辨链路互斥。「现在几点」不该经过事件分类，更不该经过知识检索——每多走一层都是额外延迟与误判风险。

#### ② 为什么情绪**不否决**事实？

初版设计把「我很焦虑」列为否决项，推回 RAG。这是错的：

> 用户说「我好焦虑，现在几点了」——时间问题是**真的**。
> 若因情绪把它推回 RAG，用户既拿不到时间，又会再次被自曝「无法联网」，**原缺陷直接复发**。

修正后的原则：**情绪影响「怎么说」，不影响「答不答」。** 事实照给，收尾从思辨邀请切换为情绪承接（不说教、不引经典）。

#### ③ 为什么邀请是「可选」而非「必附」？

用户问「现在几点」时想要的是时间。硬塞一句哲学是**另一种形式的答非所问**，与原 bug 属同类错误——都是拿人格覆盖需求。

因此规则是：**只有事实成功给出后，才允许附加一句邀请**。能力边界声明（查不到天气/位置）自带收尾，不再追加。

#### ④ 为什么默认启用，而 Freshness 默认关闭？

Freshness 是**新能力**，需观察期；Capability 是**缺陷修复**，默认关闭等于不修。
熔断开关保留：`CAPABILITY_ENABLED=false`。

## 4. 能力清单与行为契约

### 4.1 time_query（本次核心修复）

**铁律：禁止回答「我不知道时间」，禁止编造时间。**

系统时钟永远可得，`ok` 恒为 `true`，不存在失败分支。

| 子类型 | 触发示例 | 输出 |
|---|---|---|
| `time` | 现在几点 / 几点了 / 当前时间 | `现在是北京时间 2026年8月5日 11:10，星期三。` |
| `date` | 今天几号 | `今天是北京时间 2026年8月5日，星期三。` |
| `weekday` | 今天星期几 | `今天是星期三（2026年8月5日）。` |
| `relative` | 明天几号 / 昨天几号 | `明天是 2026年8月6日，星期四（今天是 2026年8月5日，星期三）。` |
| `year` | 今年是哪一年 | `现在是 2026 年（今天 8月5日，星期三）。` |

**时区处理**：云函数运行时时区不确定（常为 UTC），因此显式做 `+8h + getTimezoneOffset()` 换算，**不依赖服务器本地时区**。测试用固定时刻注入验证。

### 4.2 calculation_query

**安全铁律：零 eval / 零 new Function / 零 vm。** 用户输入永不进入 JS 执行器。
实现：归一化 → tokenizer → 调度场算法 → RPN 求值。

支持：`+ - * / ^`、括号、一元负号、`的平方/立方/N次方`、`根号/开方`、`百分之N`、`N%`、千分位逗号、中文运算词。

**歧义拒答**：中文「甲除乙」与「甲除以乙」含义相反，裸「除」一律要求澄清——**宁可拒答，不可猜一个错数**。

### 4.3 weather_query

**铁律：绝不编造天气。** 一个错的温度会让用户穿错衣服，这是真实伤害。

数据源未配置时的姿态：**声明能力边界 → 给可行替代路径 → 保留人性化收尾**，而非「我无法联网」式的自曝短板。

Provider 扩展点：`WEATHER_PROVIDER` / `WEATHER_API_URL` / `WEATHER_API_KEY`，默认 `none`。

### 4.4 location_query

**架构事实**：云函数本身没有用户位置，只能由前端 `wx.getLocation` 授权后经 `event.location` 传入。

- 已传入 → 复述事实
- 未传入 → 说明这是**需要授权**而非**我不知道**
- **拒绝 IP 归属地猜测**（IP 归属地 ≠ 用户位置）
- **隐私**：坐标/地址不写入观测日志，只记录授权状态布尔值

### 关键案例

**① 原缺陷回归**

```
输入：现在几点
输出：现在是北京时间 2026年8月5日 11:10，星期三。

      如果你愿意，我们也可以聊聊时间这件事本身——它为什么总是不够用。
```
断言：`mode=capability`、`bypass_rag=true`、`citations=[]`、
不含「无法联网 / 不知道时间 / 无法获取时间 / 我没有实时 / 获取不到时间 / 无法确定现在」。

**② 否决护栏（必须回 RAG）**

| 输入 | 判定 |
|---|---|
| 时间的意义是什么 | veto-meaning → null |
| 时间过得好快，怎么办 | veto-metaphor → null |
| 如何管理时间 | veto-lifeadvice → null |
| 我总觉得时间不够用 | veto-metaphor → null |
| 你怎么看待时间这件事 | veto-opinion → null |
| 光阴都去哪了 | veto-metaphor → null |
| 要怎么珍惜时间 | veto-metaphor → null |
| 时间的本质是什么 | veto-meaning → null |

**③ 情绪并存**

```
输入：我好焦虑，现在几点了
输出：现在是北京时间 2026年8月5日 11:10，星期三。

      看你这会儿不太好受。要是想说说，我在。
```
事实未丢失，收尾切换为情绪承接。

**④ 深夜时段感知（02:30）**

```
现在是北京时间 2026年8月6日 02:30，星期四。

夜深了。如果你是被什么事撑着没睡，可以说说。
```

**⑤ 计算安全**

| 输入 | 输出 |
|---|---|
| `1+1; require('fs')` | 拒绝（不支持的字符），不执行 |
| `10除以0` | 「除数是 0，这个式子在数学上没有定义——不是我算不出来，是它本身没有答案。」 |
| `6除3` | 「你写的"除"在中文里有两种相反的读法……你是想算哪一个？」 |
| `0.1+0.2` | `0.3`（浮点噪声已消除） |
| `根号-4` | 「负数在实数范围内开平方没有结果。」 |

**⑥ 天气不编造**

```
输入：今天天气怎么样
输出：天气这类实时数据，我这里还没有接入可信的气象数据源，所以不能给你一个具体的温度或降雨概率——
      这种事宁可不说，也不能说错，穿错衣服、没带伞都是实实在在的麻烦。
      查你所在的城市的实时天气，手机自带的天气应用或微信搜索"天气"都是几秒钟的事。
```
断言：不含任何温度数字、不含「无法联网」、含可行替代路径。

## 6. 观测字段

`observability_logs` 新增 `capability` 子对象（非能力路径恒为 `null`，向后兼容）：

```json
{
  "capability": {
    "name": "time_query",
    "sub_type": "time",
    "confidence": "high",
    "signals": ["time-pattern:time"],
    "emotional": false,
    "tool_ok": true,
    "tool_reason": null,
    "bypass_rag": true,
    "has_invite": true
  }
}
```

**隐私**：位置类只记录能力名与授权状态，坐标/地址明文绝不落库（测试项 J 强制校验）。

可观测的运营问题：
- 能力层命中率与误判率（对照 `signals` 与用户后续行为）
- `tool_ok=false` 占比 → 天气/位置数据源缺口的量化依据
- `emotional=true` 占比 → 工具诉求中夹带情绪的真实比例

## 8. 风险项

| # | 风险 | 等级 | 现状 / 缓解 |
|---|---|---|---|
| R-01 | 规则式路由存在长尾误判（口语化表达未覆盖） | 中 | 否决层从严；未命中即回原链路，误判代价是"回到修复前"而非产生错误答案；上线后按观测 `signals` 迭代 |
| R-02 | 天气/位置无真实数据源，用户诉求未被满足 | 中 | 诚实边界 + 替代路径；数据源选型列为 Phase R2 |
| R-03 | 云函数容器时钟漂移 | 低 | 依赖腾讯云 NTP；显式时区换算已消除时区类错误 |
| R-04 | 计算能力被当作科学计算器使用（三角/对数缺失） | 低 | 未覆盖的字符走诚实报错，不会给错数 |
| R-05 | 邀请文案在高频工具使用下显得啰嗦 | 低 | `CAPABILITY_INVITE_ENABLED=false` 可关；观测 `has_invite` 与用户反馈决策 |
| R-06 | 能力层与 Freshness 的边界在"最近天气异常"类问句上可能重叠 | 低 | 当前 weather 触发式要求明确气象词；重叠样本纳入 R2 评测集 |

## 9. 下一阶段（Phase R2 候选）

进入 R2 的前置条件：

1. Phase R 真实生产观测样本 ≥ 50 条能力路径请求
2. 误判率（应走 RAG 却被能力层接管）< 2%
3. 天气数据源完成合规评估（备案主体、数据授权、调用配额）

R2 候选范围：

- 天气真实数据源接入（含降级与超时策略）
- 位置能力前端授权链路打通
- 单位换算 / 汇率 / 日期差值等高频工具补充
- 规则路由 → 轻量分类器（仅在观测证明规则长尾不可控时才做）

**不做的事**：不把工具能力写进 corpus.json，不为工具能力做 embedding，不让 Prompt 承担事实生成。
