# 百问验证执行手册（Phase F 冻结版 / v0.9.1 基线）

> **评审结论**：Phase F v0.9.1 **通过，正式冻结**。F 阶段不再修改任何功能 / 标签 / 回答结构，v0.9.1 作为**百问实验基线版本**投放真实用户。
> **本手册是冻结后的唯一操作文档**：指导如何部署、如何收数据、如何判断是否可以进入 Phase G。不引入任何新功能——决定产品方向的不再是开发者判断，而是第一批用户留下的数据。

| 数据可比性 | 所有 100 问必须来自同一份代码（v0.9.1），中途不改 |

## 1. 完整数据追踪链（已闭环）

```
用户问题
   ↓
question_logs          （openid / question / mode / category / emotion / theme / strategy / routeThemes / answer_id）
   ↓
AI 生成回答
   ↓
answer_id              （YYYYMMDD_xxxx，模型 / 本地 / 超时回退 统一出口 generateAnswer）
   ↓
answer_feedback        （量化：👍有帮助 / 👎没帮助 + 点踩原因）
   ↓
answer_quality_log     （定性：为什么有效 / 无效，可选自由文本）
   ↓
admin 洞察             （categoryBreakdown + 有帮助率 + 点踩原因 Top + quality.failures/goods）
   ↓
知识资产优化           （反哺 analyzeQuery 词库 / actionLibrary 行动 / 引用策略 / metadata.user_questions）
```

**关键工程收口**：所有回答路径（model / local / localOnly-fallback）都经过 `generateAnswer` 出口，因此**任何回答都有 `answer_id` 可追溯**——避免了"正常回答有日志、异常回退无日志"导致的数据污染。

---

## 2. answer_id 设计确认（评审通过）

格式：`YYYYMMDD_xxxx`（例：`20260726_a83f`）

| 优点 | 说明 |
| --- | --- |
| 可读 | 人工排查日志时直接知道日期，便于按日分析模板 / 模型效果 |
| 可扩展 | 未来可关联 `model` / `mode` / `prompt_version` / `retrieved_books` / `feedback`，例如统计"classic 模式平均满意度 vs plain" |
| 统一出口 | 模型 / 本地 / 超时回退都经 `generateAnswer`，闭环完整，无数据盲区 |

三层（`question_logs` / `answer_feedback` / `answer_quality_log`）通过 `answer_id` 关联，未来可回答"哪种模板 / 模式满意度最高"等问题。

## 3. 点踩快捷原因 chips（评审通过）

点踩后展示 5 项规范原因（自由文本补充仍可选，不强迫填写）：

- ☐ 太抽象
- ☐ 没解决我的问题
- ☐ 引用太多
- ☐ 缺少行动建议
- ☐ 理解错了

**预测**：「太抽象」可能成为最高频——思想类 AI 最大风险是用户"我懂你的道理，但我要怎么办？"。G 阶段重点可能不是增加经典，而是 **经典思想 → 现实解释 → 具体行动** 的落地。

## 5. 真实用户验证执行计划

### 5.1 第一轮：10 人探索（不看数量，看行为）

**目标**：不是凑数，而是观察真实使用行为。

重点看：
- 用户**第一次**会问什么？（记进 question_logs 的 question 字段）
- 用户是否**愿意继续追问**？（对话历史 / followUp）
- 哪些回答被**收藏 / 截图**？（定性信号）
- 哪些地方**觉得像 AI**？（点踩原因 + 自由文本）

第一轮不追求配额，目标是发现"我们没想到的问法"和"明显不对劲的回答"。

### 5.2 第二轮：100 问正式样本（5 类各 20）

| 类别 | 配额 |
| --- | --- |
| 人生方向 | 20 |
| 学习成长 | 20 |
| 情绪压力 | 20 |
| 关系问题 | 20 |
| 长期选择 | 20 |

- 进度直接看 admin 看板 `categoryBreakdown`（每行 `count/20` 进度条）。
- 完全无关键词命中的问题归入「未分类」，不偷偷堆进某类，保证进度可信。

## 6. 百问期间观察指标

### 6.1 已自动化采集（admin 看板直接看）

| 指标 | 数据来源 | 看板位置 |
| --- | --- | --- |
| 五类桶进度 | `question_logs.category` | categoryBreakdown |
| 理解准确率（有帮助率） | `answer_feedback.helpful` | 有帮助率 |
| 行动有效率 | `answer_feedback` + 负向 reason | 点踩原因 Top |
| 引用接受度 | `answer_feedback.reason=="引用太多"` | 点踩原因 Top |
| 定性失效信号 | `answer_quality_log.failureReason` | quality.failures |
| 定性成功信号 | `answer_quality_log.goodPoint` | quality.goods |

### 6.2 需人工观察 / 后续埋点（v0.9.1 未自动采集）

> 这三项是最有价值的"思想助手"指标，但 v0.9.1 基线**尚未自动埋点**，当前靠人工观察，Phase G 可补 instrumentation。

| 指标 | 当前怎么看 | G 阶段可补 |
| --- | --- | --- |
| **二次追问率** | 从 `question_logs` 按 openid + 时间序手动看连续提问；或读对话历史 followUp | 加 `repeatAskRate` 聚合（同 openid 短间隔连续问题占比） |
| **引用展开率** | 引用卡展开交互当前未埋点，靠截图 / 观察 | 加引用卡"展开"点击事件 |
| **用户语言变化** | 纯定性：读同一用户 question 字段的时间序（如"人生没意义"→"我是不是该先调整行动"） | 暂不埋点，靠抽样阅读 |

### 6.3 周度复盘清单（建议每周一次）

- [ ] 五类桶进度到多少？（离各 20 还差多少）
- [ ] 有帮助率趋势？（升 / 降 / 持平）
- [ ] 点踩原因 Top3 是什么？（"太抽象"是否最高频）
- [ ] quality.failures 里有没有**反复出现**的失败模式？
- [ ] quality.goods 里有没有**可复制**的成功回答特征？
- [ ] 有没有"我们没想到的问法"值得记进 user_questions？

## 7. Phase G 开启条件（数据驱动，非时间驱动）

**硬门槛（全部满足才启动 G）**：

| 门槛 | 含义 |
| --- | --- |
| 100 真实问题 | 五类基本覆盖，categoryBreakdown 接近满 |
| 50 有效反馈 | `answer_feedback` 至少 50 条（量化层可信） |
| 20 个明确失败案例 | `answer_quality_log` 中能归类的失效回答（点踩 + 明确原因） |
| 10 个高价值用户问法 | 反复出现 / 启发大的真实问法，纳入 `metadata.user_questions` |

**达成后**启动 G-1 / G-2 / G-3（详见 `docs/10` §9.3）：
- G-1 查询理解优化（百问反哺口语→标准问题→思想主题）
- G-2 回答策略优化（按反馈调五段比例与深度）
- G-3 小规模真实用户测试（20~50 人观察留存 / 二次提问）

**不达标不开 G**：即使时间过去，也不靠"感觉"改产品。

## 8. 部署清单（与 v0.9.1 一致，勿漏）

1. 重新上传部署 **chat + admin + feedback** 三个云函数（右键→上传并部署·云端安装依赖）；
2. 云开发控制台**手动新建 `answer_quality_log` 集合**（未建会报 COLLECTION_NOT_EXIST）；
3. `question_logs` / `answer_feedback` 新字段（answer_id / category / failureReason 等）云库无 schema、自动兼容；
4. **运行环境为 Node 16（无法升级）**：代码已用 `nodeFetch`（基于 `https`）兼容，无需 Node 18+；别再去云控制台调改不了的运行设置；
5. 微信公众平台 request 合法域名加入 `api.hcnsec.cn`（真机未勾"不校验"时缺此项会静默拦截）；
6. `archive/` 旧脚本**禁止运行**（会重生成旧敏感 corpus 覆盖现有哲学语料）。
