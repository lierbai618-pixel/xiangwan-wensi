# 04 技术架构

> 目的：让接手的人快速理解"为什么是这样"，而不是重写架构。

## 总览

```
用户提问
   ↓
KnowledgeProvider（数据源抽象）
   ├─ LegacyProvider：读 corpus.json（旧）
   └─ KnowledgeBaseProvider：读 chunks 集合（新）
   ↓
Retriever（检索）
   ├─ 词法 + 余弦打分
   └─（Phase E）意图分类 → 多库融合
   ↓
Citation（引用封装）
   └─ display_text / source_position / verified
   ↓
LLM（生成，受 AI 回答规范约束）
   ↓
思辨式回答
```

## 为什么这样分层

- **KnowledgeProvider 抽象**：数据源可替换（旧 corpus / 新库 / 未来向量库），切换不影响上层。
- **Retriever 与 LLM 解耦**：检索质量可独立评测、独立升级（Phase E 的意图分类不影响生成）。
- **Citation 独立封装**：引用信息结构化，前端可点开溯源，且原文 / 解读可分离。
- **内容无关**：整套架构不绑定任何特定知识内容，换语料即可换产品方向。

## 关键模块（现状）

- 云函数 `chat`：调度检索 + 生成，含 `msgSecCheck` 双闸（入参 / 出参）。
- 云函数 `ingest`：文本（txt / md）入库 → `documents` + `chunks`。
- 云函数 `admin`：模型配置；`history` / `login` / `feedback`：会话与轻登录。
- 数据集合：`documents` / `chunks` / `citations` / `audit_log`。
- 前端：`pages/chat` 等；`app.json` 配置。

## Prompt 位置

`chat/rag.js` 的 `rolePrompt` 是唯一核心 Prompt，按 `05-开发路线图.md` Phase B 拆为
System / Identity / Goal / Style / Workflow / Safety / Output Format，
仅 `Style` 段可常改，不影响 `Workflow`。
